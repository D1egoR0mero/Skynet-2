# User Stories: Skynet Internship Finder — Light and Dark Theme Switching

## US-003 — Switch between a light and dark presentation of the listing page

**Story:** As a student browsing internship listings, I want to switch between a light and dark presentation, so that I can read the listings comfortably in different lighting conditions and my choice is remembered.

**Acceptance Criteria**

1. Given a browser that has never loaded the page and therefore holds no `skynet-dark` entry in local storage, when the student opens the page and the listings finish loading, then the page is presented in the light theme — `body` carries no `dark` class, panels render on the white `--panel` value, text uses the dark `--text` value, and the page background is the light `--bg` value — the header control shows the visible label "☾ Dark mode" without the student interacting with it, the control's accessible name is "Toggle dark mode", and nothing is written to local storage as a result of loading the page.

2. Given the page is showing the light theme, when the student activates the theme control once, then the `dark` class is added to `body`, the dark token values declared for `body.dark` take effect (panel `#202a40`, text `#edf2ff`, muted `#a7b3ca`, lines `#35425a`, page background `#151d2d`) so the page switches to the dark presentation, the `skynet-dark` entry holds the JSON boolean serialised as the exact string `"true"`, the control's visible label becomes "☀ Light mode", and the switch completes in the current page load with no reload and no network request.

3. Given the page is showing the dark theme because the student has already activated the control, when the student activates the control again, then the `dark` class is removed from `body`, the light token values from `:root` are back in effect so the page is presented in the light theme, the `skynet-dark` entry now holds the exact string `"false"`, and the control's visible label returns to "☾ Dark mode"; activating the control a third time returns the page to exactly the state described in criterion 2.

4. Given the `skynet-dark` entry holds `"true"` before the page is opened, when the student opens or reloads the page and loading finishes, then the page is presented in the dark theme with no control activation required, and the control's visible label already reads "☀ Light mode"; the search, Include keywords, Exclude keywords, Location, Opportunity type, and Posted-since controls start empty, the Explore view is selected, and the results show page 1, because the colour theme and the saved-role set are the only preferences carried across the reload.

5. Given the `skynet-dark` entry is absent, holds JSON `null`, or holds text that is not parseable JSON — for example the bare word `dark`, the fragment `{oops`, or an empty string — when the student opens the page, then the light theme is presented exactly as in criterion 1 with the visible label "☾ Dark mode", no error message, warning, or error text appears anywhere on the page, no uncaught script error occurs, the listing cards, available-roles counter, matching-results counter, saved counter, and pagination indicator all render normally, and activating the theme control still works as described in criterion 2.

6. Given the student has typed text into the search box, Include keywords, Exclude keywords, and Location, has selected an Opportunity type and a Posted-since window, has switched to the Saved roles view with two roles saved, and is viewing a results page later than page 1, when the student activates the theme control in either direction, then only colours change: the six control values are unchanged, the Saved roles view remains selected with the Explore entry still inactive, the pagination indicator still reads the same page number and total, the available-roles counter, matching-results counter, and both saved counters keep their previous values, the saved-role set is unchanged, and the visible cards are the same listings in the same order with none added, none removed, and none reordered.

7. Given the student has switched the page to the dark theme in one browser, when the student opens the page in a different browser or in a browser profile whose local storage has been cleared, then that browser presents the light theme with the visible label "☾ Dark mode", because the preference is stored only in that browser; no account setting, server endpoint, cookie, or request payload carries the theme between browsers, so changing the theme in one browser leaves the other unchanged and the listing request itself is identical in both themes.

8. Given the theme control is a native `<button>` inside the page header, when the student reaches it by pressing Tab from the browser's address bar or from the preceding focusable control and then presses Enter, and separately presses Space, then the control receives focus, is announced with the accessible name "Toggle dark mode" supplied by its `aria-label`, and each key press toggles the theme exactly once, as confirmed by the `skynet-dark` value and the visible label changing exactly as described in criteria 2 and 3; the visible text always names the mode the control will switch to — "☾ Dark mode" while the light theme is showing and "☀ Light mode" while the dark theme is showing — while the accessible name stays constant across both states.

**Priority:** Should-have (MoSCoW) — the theme toggle is not one of the headline capabilities in `README.md`'s feature list, but `US-001` acceptance criterion 10 already requires that the control switches the page between light and dark presentation, that its label reflects the new mode, and that the choice survives a reload, so the product cannot satisfy its parent story without this behaviour.

**Assumptions / dependencies:**
- The page is styled from a single stylesheet, `public/style.css`, served directly as a static file with no build step, bundler, preprocessor, or second theme stylesheet; the light values are declared once on `:root` and the dark values are declared once on `body.dark`, so those two blocks are the only theme definitions and no third-party styling participates.
- The theme is chosen in the browser from the stored preference alone. The page does not consult the operating system's colour-scheme preference, so a student whose OS is set to dark still gets the light theme until they activate the control; criterion 1 describes the unset-preference case only.
- There is no server or API involvement: no theme endpoint, query parameter, cookie, or account field exists, the `GET /api/listings` response is identical in both themes, and no network request is made when the control is activated.
- The `skynet-dark` key holds a JSON-serialised boolean, written as `"true"` or `"false"`; an absent key, JSON `null`, or unparseable text is treated as "not dark" rather than as an error.
- Layout, spacing, and content are identical in both themes: the dark block re-declares only the five colour custom properties, so no element is hidden, added, removed, reordered, or resized when the theme changes.
- The other controls, the saved-role set, and pagination behave exactly as documented in US-001 criteria 1–9 and US-002; activating the theme control does not re-run filtering, sorting, or pagination, which is why criterion 6 requires the rendered cards to be untouched.
- The page obtains its listings from the application's own `GET /api/listings` endpoint in the same Node.js process, so criteria 1, 4, 5, and 6 assume listings load successfully as described in US-001 criteria 1 and 9.
- Coverage: the test named "PM2.1 favorites and theme persist and restore through storage" in `test/pm21-ui.test.js` asserts criteria 2 and 4 (the stored value is `"true"` after activation, and a fresh browser seeded with that storage has `dark` on `body`); criteria 1, 3, 5, 6, 7, and 8 have no automated test on this branch and must be verified by inspection or demonstration.
