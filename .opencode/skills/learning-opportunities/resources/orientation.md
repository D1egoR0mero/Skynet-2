# Repo Orientation: Skynet-2 (Skynet Internship Finder)

> Generated by orient. Re-run to update.

## One-line purpose

A terminal (CLI) prototype that helps Virginia Tech students find internships by searching a public internship dataset and narrowing results with an interactive, funnel-style filter — built to explore features that Handshake lacks.

## Primary language(s)

- **JavaScript** (Node.js, ES modules) — the entire application in `src/`. `package.json` declares `"type": "module"` and there is no `tsconfig.json`, so this is plain JS, not TypeScript.

## Pipeline / workflow stages

1. **Fetch** — `src/sources/simplify.js` downloads a public JSON listing file from GitHub over HTTP.
2. **Normalize** — each raw record is mapped into one shared listing shape (see *Core concepts*).
3. **Interactive funnel** — `src/index.js` runs a loop: pick one filter → apply it → see the smaller pool → repeat, undo, or finish (at least one filter is required).
4. **Filter** — `src/filters.js` provides pure functions that keep or drop listings based on keyword matching over a single field.
5. **Display** — `src/display.js` paginates the surviving pool (20 per page) and lets the user move with `n` / `p` / `q`.

## Core concepts

**The listing contract**: Every source must return objects shaped `{ title, company, location, url, datePosted, terms, tags, source }`. `src/sources/simplify.js` documents this contract in its header comment; `filters.js` and `display.js` assume exactly these fields.

**Source adapter**: Each data provider is isolated behind a `fetchInternships()` function that returns the shared shape. Adding a new provider (e.g. a company API) means writing one more adapter and pushing its results into the same array — nothing downstream changes. Lives in `src/sources/`.

**Funnel filtering**: No scores or weights — each filter step simply narrows the current pool. Include keywords match with **AND** logic (all must appear); exclude keywords match with **OR** logic (any one removes the listing). Implemented in `src/filters.js` (`matchesAll` / `matchesNone`).

**Undo stack**: `src/index.js` keeps a `history` array of pools, one entry per applied filter. "Undo last filter" pops the last pool off the stack, so every applied narrowing is reversible.

**Field-based text matching**: Filters search a single string field of the listing. `applyKeywordFilter` takes a `field` option; most filters search `tags` (title + company concatenated and lowercased), while the location filter searches `location`.

## Common gotchas

- **`tags`, not `title`.** `applyMajorFilter`, `applyCompanyTypeFilter`, and `applyPlusMinusFilter` all search the `tags` field — title and company text concatenated in `simplify.js`. The docstring above `applyKeywordFilter` says `field: "title"`, but the actual default is `"tags"`. There is no separate "field of study" field, so major matching is best-effort text matching.
- **Leftover debug line.** `src/filters.js` has a stray `console.log(inc)` inside `applyKeywordFilter` (around line 30) that dumps the parsed include keywords to the console every time any filter runs.
- **Live network fetch, no cache.** The app always fetches the listing JSON from a GitHub raw URL at startup. With no network the run aborts with a red error message and returns — there is no local fixture or offline mode.
- **Zero-result guard.** In `src/index.js`, a filter that would leave 0 listings is *rejected* rather than applied, so the pool can never become empty through filtering.

## Suggested exercise sequence

### Exercise 1 — Understand the intended search semantics

Open `README.md` and read the **Include Keywords** and **Exclude Keywords** sections (through the "Example" section). Ignore the code for now and focus on the described behavior.

Then, without looking back, explain in your own words to a non-developer: why does the include list require *all* keywords to match while the exclude list removes a listing if *any* one matches? Give one short example of a listing that would pass and one that would be removed.

### Exercise 2 — Read the data contract

Open `src/sources/simplify.js`. Read the header comment and find the `.map(...)` call that builds each listing object. Write down every field the app puts on a listing.

Then answer: based purely on those fields, what kinds of searching and filtering does the rest of the app *allow* itself to do? Name one useful filter the current listing shape would make hard or impossible, and say why.
